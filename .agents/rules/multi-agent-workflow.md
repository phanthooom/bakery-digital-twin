# Регламент многоагентной оркестрации (Multi-Agent Workflow)

Этот документ определяет правила взаимодействия главного агента-оркестратора и специализированных субагентов в Google Antigravity для проекта `bakery-digital-twin`.

```mermaid
flowchart TD
    User([Пользователь]) -->|Запрос / Задача| Master[Главный агент: Orchestrator]
    Master -->|1. Анализ и декомпозиция| Arch[Субагент: Architect]
    Arch -->|План реализации| Plans[Папка /plans/*.md]
    Plans --> Master
    Master -->|2. Реализация по TDD| Eng[Субагент: Engineer]
    Eng -->|Код и тесты| Master
    Master -->|3. Аудит и проверка качества| Rev[Субагент: Code Reviewer]
    Rev -->|Замечания / Доработки| Eng
    Rev -->|APPROVED (LGTM)| Master
    Master -->|Итоговый отчёт и артефакты| User
```

---

## 1. Роли и зоны ответственности

### Главный агент (Master Orchestrator)
- **Функция**: «Дирижёр» оркестра агентов.
- **Обязанности**:
  1. Принимает текстовый промпт пользователя, определяет цели и масштаб задачи.
  2. Координирует работу субагентов через системный инструмент `invoke_subagent` и обмен сообщениями `send_message`.
  3. Контролирует ведение планов и статусов в каталоге `plans/`.
  4. Следит за разрешением замечаний между `engineer` и `code-reviewer`.
  5. Формирует финальный структурированный ответ пользователю с ссылками на изменённые файлы и результаты тестирования.

### Субагенты (Subagents)

| Агент | Файл манифеста | Основная роль |
|---|---|---|
| **`architect`** | `.agents/agents/architect/agent.md` | Проектирует архитектурное решение, сверяет соответствие `docs/adr/` и `GLOSSARY.md`, декомпозирует задачу на подзадачи с TDD-стыками, создает/обновляет файл плана в `plans/`. |
| **`engineer`** | `.agents/agents/engineer/agent.md` | Пишет код строго по TDD (Red-Green-Refactor) на согласованных стыках, обеспечивает компиляцию TypeScript и прохождение тестов (`npm test`, `npm run typecheck`). |
| **`code-reviewer`** | `.agents/agents/code-reviewer/agent.md` | Проводит строгий аудит изменений (соответствие ADR, чистота типов, отсутствие деградации производительности в 3D R3F, соблюдение глоссария). Выносит вердикт `APPROVED` или `CHANGES_REQUESTED`. |

## 2. Стадии жизненного цикла задачи (Orchestration Pipeline)

### Фаза 1. Приёмка и первичный анализ
1. Мастер-оркестратор проверяет входящий запрос.
2. Если задача тривиальная (простая справка, вопрос по документации) — отвечает напрямую без вызова субагентов.
3. Если задача требует изменения логики, конфигов или архитектуры — активирует оркестр.

### Фаза 2. Проектирование (Architect)
1. Оркестратор запускает субагента `architect`:
   - Передаёт постановку задачи, контекст `CLAUDE.md`, `GLOSSARY.md` и ссылки на релевантные ADR.
2. Архитектор:
   - Анализирует затронутые стыки системы (`packages/shared`, `web`, `simulator`, `config`).
   - Создаёт файл плана в `plans/YYYY-MM-DD-<slug>.md` по шаблону `plans/template.md`.
   - Возвращает план и декомпозицию.

### Фаза 3. Реализация (Engineer)
1. Оркестратор запускает субагента `engineer`, передавая утверждённый план.
2. Инженер:
   - Пишет unit-тесты для нового поведения (Red).
   - Реализует минимальный чистый код (Green).
   - Выполняет рефакторинг.
   - Запускает валидацию:
     ```bash
     npm test
     npm run typecheck
     ```
   - При успехе переводит пункты плана в статус `[x]` и отчитывается Оркестратору.

### Фаза 4. Ревью качества (Code Reviewer)
1. Оркестратор запускает субагента `code-reviewer` со списком диффов и затронутых файлов.
2. Ревьюер проверяет чек-лист (ADR, TDD-стыки, типизация, 3D-производительность, глоссарий).
3. **Цикл обратной связи**:
   - Если вердикт `CHANGES_REQUESTED`: Оркестратор возвращает замечания инженеру `engineer` для исправления, после чего ревьюер проверяет повторно.
   - Если вердикт `APPROVED (LGTM)`: задача готова к финализации.

### Фаза 5. Финализация
1. Оркестратор фиксирует статус плана `COMPLETED`.
2. Предоставляет пользователю итоговый отчёт с кликабельными ссылками на изменённые файлы и подтверждением прохождения всех тестов.

## 3. Управление планами и состоянием (`plans/`)

Все промежуточные и итоговые состояния задач фиксируются в директории `plans/` в корне проекта.

- **Именование файлов**: `plans/YYYY-MM-DD-<краткое-имя-задачи>.md`
- **Жизненный цикл статуса плана**:
  `DRAFT` → `READY_FOR_DEV` → `IN_PROGRESS` → `REVIEW` → `COMPLETED`
- Файл плана должен содержать:
  1. Цель и требования.
  2. Затронутые модули и ADR.
  3. TDD-стыки и планируемые тесты.
  4. Чек-лист реализации с отметками прогресса.
  5. Вердикт код-ревью.
